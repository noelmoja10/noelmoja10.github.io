Artifact description and origin

Weight Progress is the Java Android application I developed in CS 360 Mobile Architecture and Programming during the May–June 2026 term. It supports local accounts, dated weight records, history editing, weight-loss goals, and optional SMS alerts. This enhancement adds moving averages, daily trend analysis, and conditional goal-date estimates. The source package preserves the original artifact and the pre-analytics UI Preview alongside the enhanced project. It also carries forward the recent onboarding, validation, lbs/kg, Me account controls, and stationary bottom-navigation improvements.

Selection and demonstrated skills

I selected this artifact because its dated measurements present an algorithmic problem with a visible result. A single weigh-in does not explain the pattern across a history. The new Home trends card connects my interest in front-end development with the calculations needed to present useful information. My QA background also makes boundary cases and clear explanations of unavailable results important to this work.

The analyzer sorts a defensive copy by date, then uses an ArrayDeque and a running sum to calculate moving averages in one traversal. Java documents most ArrayDeque operations as amortized constant time (Oracle, n.d.). Each value enters once and leaves at most once. Compared with repeatedly scanning each window, the averaging pass improves from O(nw) to O(n) when treating window size as variable. Sorting makes the complete analysis O(n log n) in the worst case. The deque requires O(min(n,w)) space; the copied data and returned points make total additional space O(n).

During that traversal, centered running moments calculate a least-squares daily slope using elapsed calendar days. This handles irregular dates without assuming daily entries. The fitted rate is extrapolated from the latest recorded weight, and explicit rules suppress unsuitable estimates. The average selector changes smoothing over 3, 7, or 14 entries; regression still uses all recorded observations. Results are calculated on a worker thread and converted to the preferred unit only for display.

Course outcomes and coverage plans

Outcome 3 is the main focus: selecting a deque, comparing algorithmic complexity, and verifying date-aware calculations demonstrate the planned algorithms-and-data-structures enhancement. Outcome 2 is supported by this narrative, pseudocode, design notes, and clear screen labels. Outcome 4 is supported by integrating the engine into the working application and testing its results against independent reference implementations. The 20,000-entry comparison checks every moving average; its operation counts illustrate the tradeoff, not a measured wall-clock speedup.

For outcome 5, the engine rejects mixed-account inputs, non-finite measurements, duplicate dates, and invalid or future dates. Configuration and history-size limits bound the engine’s work, while the existing session check prevents stale results after logout. These measures provide security-related evidence without claiming a security certification. The planned coverage remains outcomes 2, 3, 4, and 5; this individual enhancement does not establish full evidence for outcome 1. Room, goal history, and further migration testing remain for the database milestone.

Reflection on learning and challenges

This work reinforced that the meaning of data must guide the algorithm. Treating entry position as time would distort a trend when weigh-ins are irregular. Similarly, a seven-entry average is not a seven-day average, so the interface states that distinction. A test also exposed floating-point noise that could push an exact estimate one day late. Normalizing values extremely close to an integer before rounding resolved that boundary case and provided a useful regression test.

Another challenge was deciding when not to display a prediction. Least-squares models can be sensitive to outliers and poor at extrapolation (NIST/SEMATECH, n.d.). The implementation requires sufficient history, checks direction and freshness, and limits the displayed horizon to one year. These are product safeguards, not validated medical thresholds. The original plan suggested filtering invalid records; I instead reject an invalid dataset as a whole to avoid silently changing its apparent trend. Estimates remain separate from the user’s chosen target date and are labeled as assumptions, not guarantees. Instructor feedback and subsequent benchmarking are discussed in the publication update below; broader device testing remains.

Publication update after instructor review

My instructor recognized the ArrayDeque and running-sum implementation as evidence of thoughtful data-structure selection and efficiency, and recommended measuring the analyzer with different history sizes. I addressed that feedback in the later Milestone Four build while retaining the original analytics implementation. The Milestone Three verification passed 94 unit tests and 47 emulator tests; later results are reported separately in the project case study.

The benchmark used reproducibly shuffled synthetic histories with 10, 100, 1,000, and 10,000 daily records and a seven-entry moving-average window. Each workload received five warmups and eleven timed samples on one Android 15/API 35 ARM64 emulator in a debug build. The following measurements cover the full analyzer, including sorting, moving averages, and regression, rather than only the averaging pass.
