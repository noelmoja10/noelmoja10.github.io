Artifact description and origin

Weight Progress is a Java Android app I created for CS 360 Mobile Architecture and Programming in May-June 2026. It allows users to register and sign in to a local account, add daily weights, set a weight-loss goal, edit and delete history entries, and request an SMS on achieving the goal. For the Milestone Two enhancement, I separated the screen-specific behavior, state, and persistence while retaining the original Java/XML code and SQLite DB. The original code is attached for comparison with the improved version.

Selection and demonstrated skills

I chose the Weight Progress feature that engages my interest as a Software QA Engineer in user-facing interfaces. By reviewing requirements, edge cases, and defect reports, I realized that reliable behavior matters at least as much as look and feel, and the product demonstrates that in action. It also has a strong front-end that I hope to develop and test as a QA engineer, familiarizing myself with its logic.

The revamped MainActivity now uses dedicated Activities for each screen, delegating database reads/writes to the ViewModel. It utilizes LiveData to expose state-driven UI updates, featuring UI-driven validation with reusable validation logic and a repository interface, while database writes and password verification occur on a background thread. The ViewModel retains information relevant to the UI when the system recreates an Activity (Android Developers, n.d.-c). While the architecture feels heavier than before, it is more testable and future-proofs the application better, preparing it for analytics and database-related development.

The quality of the outcome speaks for itself: failed saves can be retried, invalid fields show feedback while retaining user input, and an incorrectly entered weight-and-goal combination reverts both values. When editing a note, the displayed weight is 181.26, not the rounded 181.3. Saving a draft will persist it through activity recreation, with passwords being exempt from state saving (Android Developers, n.d.-b). All that is needed is separation of concerns, dependency injection, state management throughout an activity lifecycle, and regressions prevented with unit tests.

Course outcomes and remaining coverage

This enhancement offers the intended software engineering evidence for Outcomes 2,3,4,5, though no outcome is claimed to be mastered completely. The support for Outcome 2 is found in the narrative, architecture documentation, and the reproducibility of test instructions. Demonstration of tradeoffs in the decisions supports Outcome 3; options considered include a serial executor vs. parallel, retained state vs. reauthentication on process death. Implementation of the repository boundary, ViewModels, validators, and tests manifest Outcome 4. Specifically, 43 local unit tests and 20 Android instrumentation tests passed, and the debug build + lint check also succeeded.

For Outcome 5, the enhancement enforces user-scoped access to records, safe error messages to users, exclusion of password state, and restrictions on backup. Android’s backup documentation guided the distinction between legacy backup settings and newer cloud/device transfer rules (Android Developers, n.d.-a). Existing salted password hashes and parameterized SQL are retained as protections; they are not new achievements. Outcome 1’s coverage is partial – the instructor’s feedback on Milestone One contributes to this enhancement, but it does not offer evidence of the team’s collaboration practices. The same holds true for Outcome 2’s coverage. In all cases, the same coverage plan as before is followed: moving averages and trend analysis are reserved for the algorithms milestone; Room, goal history, and migration testing are reserved for the database milestone.

Reflection on the enhancement process

The main lesson that I learned from this refactoring is that splitting the code into smaller files is not sufficient. It is also vitally important to set the boundaries within which one or another part of code operates. For instance, it should be clear who is responsible for a particular piece of state, who is going to write a certain value somewhere, and what the user should see if something goes wrong. Screen recreation during an unfinished save was an important detail because a form should not be submitted twice on the same data. Keeping the ViewModel and testing the recreation while there is an ongoing save mitigates that issue. Another thing that I have learned is related to precision. The value that has been formatted for display is not necessarily the one that the user wants to write into the database.

The current work allows differentiating between successful persistence and an optional following action. In case of an SMS issue, the app should not indicate that a saved weight has been lost, and requesting a text does not equal delivering it. I am using tests with fake records and a mock notification gateway – the actual carrier’s behavior has not been tested. There are still lint warnings related to texts, resources, the layout, and toolchain upgrade. It is important to proceed with wider device testing and accessibility checks as well. The code-review feedback from the instructor was not asking for particular changes, so I followed their proposal for the architecture plan. Before the final push, I will examine the working changes and use the additional instructor feedback to polish the code.
