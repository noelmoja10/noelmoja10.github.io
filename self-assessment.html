Professional direction

I am pursuing my computer science degree to switch from software quality assurance into the front-end field. I initially intended to become a full-stack developer because of the range of this job. However, while studying this subject, I discovered that my primary area of interest is implementing interfaces that people interact with on a daily basis. Still, I find the processes of developing algorithms and databases for applications highly fascinating, as well they fundamentally supplement the properties of a given interface. After graduating, I want to continue strengthening my front-end expertise, specifically in TypeScript, and expand my practical skills in the field. My portfolio presents these aspirations, as well as my QA experience, which highlight my abilities in reviewing and improving products.

Learning through computational graphics

The CS 330 Computational Graphics and Visualization class provided me the opportunity to turn a design concept into practice by building an image out of code. By using a framework provided by the course (C++ and OpenGL), I was able to put together a 3D scene, which included a desk with a laptop, a monitor, a mouse, a notebook with a pen, and a water bottle. The application uses a number of primitives meshes with transformations applied, materials, textures, and lighting to create a scene with keyboard and mouse controls for the camera as well as perspective and orthographic views. Learning to break down familiar objects into primitives helped me engage with the process of building a complex image step-by-step. At the same time, separating the processes of scene creation and viewing allowed me to think about the components that affect the final appearance. While the application is not a web-based project, it helped me experiment with the connection between calculations and visuals. For my career goals as a front-end developer, understanding the interplay between code and appearance is critical in ensuring that the implementation supports the intended vision.

Collaboration and communication

My QA work has taught me that collaboration usually starts with an upcoming feature. When a product manager shows what the coming function should do, I begin brainstorming what tests to write and what actions the application will take that the requirements did not state. As the developers implement the feature, more questions arise. We turn to the product manager to define what behaviors our tests should be looking for instead of making up answers for undocumented edge cases. Additionally, I do extensive testing of the developers' tickets and find issues during this work. My role is to contribute the user's perspective to these discussions and point out gaps in the requirements. This allows the team to think through what behaviors we want the feature to have and what defects need to go back into the code.

The capstone gave me another opportunity to practice explaining my work. My code review shows what behaviors the original application had, what weaknesses it had, and what improvements I planned. The narratives let the reader know why I made the decisions I did, while my portfolio shares the work in a more accessible way. Both required me to think about who my user was and what they needed. A code reviewer is looking for implementation details, whereas someone studying my portfolio would appreciate a description of the work and a way to find out more details. The capstone was an individual project, so my instructor's guidance did not replace the collaboration I do at work but added to it.

Evaluating and testing software

I am now able to think through implementations in terms of what can be tested and sustained. In Weight Progress, decoupling the screens, ViewModels, validation, and repository layers gave me multiple levels on which to verify behavior independently from the UI. Unit tests written through iterations helped establish normal scenarios as well as responses to invalid data, lifecycle events, and account limits. The October 3 database build passed 100 unit tests and 79 emulator tests. These results give a baseline of confidence without guaranteeing support for every device or use case.

The algorithms class helped me develop a sense of tradeoffs and avoid premature judgments on an implementation’s efficacy. Using an ArrayDeque and a running sum makes the averaging pass O(n), compared with O(nw) for repeated scans of a window of size w across n records. For a fixed window size, both passes are linear in n; sorting makes the complete analysis O(n log n). Using elapsed calendar days rather than entry positions preserves the temporal relationships between irregular measurements. After my professor suggested analyzing the algorithm’s performance characteristics, I was able to augment the code to run exploratory benchmarks for 10-10,000 entries and empirically observe the differences. Finally, Room entities, DAOs, indexes, and transactions made database relationships more discoverable. Saving revisions of goals and verifying migrations to newer versions of the schema were important parts of designing a system which respected user data.

Security and responsibility

The program helped me develop a better habit of questioning if everything that could go wrong was handled before calling something finished. For the capstone, this meant making sure that inputs were valid, queries were scoped to the currently-signed-in account, salted password hashes were kept in the database, and re-authenticating under sensitive operations. Database tests check account isolation and verify rollback when a multi-step operation fails. I had to learn the difference between what the program does to keep things safe and what I should claim it does: Room does not encrypt the stored database, and automated tests passing do not guarantee that production code will not have issues. The current testing only covers one emulator; there is still work to be done to account for different devices and accessibility needs. Knowing when to say that something is not done is part of communicating what I build. In the future, I will need to handle invalid states and the privacy of users’ data as well as implementing appropriate checks in the front-end code as I work on the user-facing parts of the software.

How the portfolio fits together

Weight Progress, initially designed in CS 360 Mobile Architecture and Programming in the May-June 2026 term, is the sole artifact improved upon in all three categories of the capstone. The software design enhancement offers a more testable foundation and clearer user flows. The algorithms enhancement transforms dated measurements into explained trends, and the database enhancement aids in the maintenance of records and goal revisions. The original source offers the comparison point, the enhanced sources, narrations, and a code review offer the progression. Along with my CS 330 learning and workplace collaboration, this work offers evidence across areas of collaboration, professional communication, algorithm evaluation, software development, and security. I want a prospective employer to see both my interest in front-end development and the QA perspective I offer to verifying if software behaves as intended.
