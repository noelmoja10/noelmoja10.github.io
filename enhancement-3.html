Artifact description and origin

Weight Progress is the Java Android app I built in CS 360 Mobile Architecture and Programming in the May-June 2026 term. It features local accounts, dated weight entries, goals, history editing, and optional SMS notifications. For the fourth milestone, I switched its production SQLite adapter to Room, added goal history, database queries, and migration tests. Otherwise, the new version also comprises the approved interface refinements and the moving-average and trend algorithms used in the Milestone Three. The submission includes the source code of the original and the production version before the database migration and the improved project as well for comparison.

Selection and demonstrated database skills

I chose the Weight Progress application because the option to edit a goal or upgrade the software without deleting measurements is critically dependent on reliable storage. As a front-end developer, this appealed to me since a good UI is only as strong as the data and operations it is built upon. The existing application already utilized foreign keys, parameterized SQL, and transactions. The implemented improvements build upon these features through Room entities, focused data access objects, and an adapter that preserves the repository interface from Milestone Two.

The revised model introduces a separation of users, settings, measurements, and goal revisions. Replacing a goal retires its previous revision, preserves it as history, and adds a new current revision in a single transaction. The unique account/active-slot index prevents two current goals for an account, while historical revisions have NULL active-slot values. SQLite allows unique indexes that do have entries with NULL in them (SQLite, 2026). Saving a goal with the same weight and target date does not add a new revision. The approach avoids duplicating current goal values in the settings table while retaining legacy identities for compatibility.

The DAOs expose account-specific ranges, the latest entry by date, and SQL count, min, max, and avg functions. Indexes support lookups of measurements by account and date and retrieval of the current goal. Foreign keys prevent orphaned records. The query plan tests actually utilize the created indexes. However, aggregation still visits matching records, and the report materializes the selected measurements and goal revisions. The existing repository interface remains compatible with the UI, while the Room adapter adds report queries verified by separate tests. The screens that were approved are preserved, and an additional screen to view and edit the history of goals is not introduced.

Course outcomes and coverage plans

The enhancement was implemented to meet the database-related requirements of Module One. It directly delivers outcome 4 by supporting relational modeling, Room integration, and automated verification. The outcome 5 is delivered by account-scoped mutations, bound query parameters, reauthentication for critical mutations, transaction rollback, and data-preserving migrations. The outcome 3 is addressed by assessing the index maintenance, lookup cost, and calculated versus stored summaries. The outcome 2 is delivered by this narrative, the relationship diagram, migration rationale, and a review process that can be repeated by others using the provided instructions.

The verification process includes 100 unit tests and 79 emulator tests. Specifically, there are 23 new Room/migration tests, 37 UI regression tests utilizing Room, 18 legacy-adapter tests carried over from before, and one history-size benchmark test. The legacy tests were performed to provide a baseline, not as tests for Room. By these deliveries, outcomes 2 – 5 are addressed; however, it should not be claimed that one enhancement addresses all program outcomes. Outcome 1 still requires more evidence, which I intend to deliver by demonstrating collaborative practices across the portfolio. My coverage plan remains the same, with final instructor feedback and portfolio polishing upcoming.

Reflection on learning and challenges

The most critical takeaway was that migrations require preserving the semantics of the existing data and its rows. The Android documentation recommends explicit migration paths and testing them for complex changes (Google, 2026). My migration paths were applied from legacy versions 1, 2, and 3 to database schema version 4. The tests ensure that credentials, IDs, precision, preferences, and relationships are valid after migrating and reopening the application. Legacy versions had no recorded creation time for goals, so their initial revision is migrated with the migration time instead of an undefined historical period.

The approved 700 lb input ceiling created a different trade-off. Earlier versions could accept higher numbers, and applying the new limit during migration would cut valid legacy records. The migration process preserves these values at their exact numbers, and subsequent inserts use the new guardrails. The tests prove that old records are readable, and new or edited records follow the new rules. The failures I deliberately inserted during the registration, setup, and measure-plus-goal save process tested the rollback transaction instead of saving some incorrect data.

To address my professor’s feedback on Milestone Three, I added timed runs for analyzers and database operations with 10, 100, 1,000, and 10,000 entries. The median and upper-percentile measurements supplement the complexity analysis, but a single debug emulator is insufficient to assess performance on all devices. The extended device and accessibility testing recommended after Milestone Two is still required. The Room database does not offer encryption or protection against physical compromise of a device. These limitations are explicitly stated in the review guidelines.
